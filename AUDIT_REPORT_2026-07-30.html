02

Executive summary

Zopiq is not the codebase this audit expected to find. The engineering is careful in ways most pre-launch marketplaces are not: pricing is computed in Postgres and the client is never trusted with a number; the order state machine lives in the database rather than in three apps that must agree; all 198 security definer function definitions pin search_path; auth sessions are held in the Android Keystore, not SharedPreferences. The migration comments read like design documents and repeatedly catch the authors' own earlier mistakes — the pickup OTP that was readable by the rider it was meant to test was found and closed by the team itself.

That makes the gaps stranger and more dangerous, because they are not distributed evenly. They cluster almost entirely in the commercial layer — the part of the system where money enters, moves, and leaves. The order pipeline is production grade. The ledger underneath it is not.

The four findings that decide the launch date

  1. No payment exists. Checkout runs on MockPaymentGateway, and place_order accepts any non-empty string as proof of payment. A UPI order can be placed, cooked, dispatched and delivered without a rupee moving. (PAY-001)
  2. A restaurant can mint money. Since migration 0064 a vendor may create its own discount code. Settlement pays that vendor sum(subtotal) − commission; the discount is never deducted from anyone. A vendor issuing a 100%-off code on its own menu is settled roughly 80% of full menu price by the platform, on every order, without limit. Coupons additionally have no per-user cap, no total cap and no expiry by default. (BIZ-001, BIZ-003)
  3. Cash on delivery loses the whole order value. COD is a live payment method. No table, column or function anywhere tracks cash collected, cash in a rider's hand, or cash deposited. The weekly rider payout pays the rider their earnings while they still hold the customer's cash; the weekly settlement pays the vendor in full from platform funds. (BIZ-002)
  4. Anyone on the internet can push a notification to every user you have. send-notification is deployed with JWT verification off and performs no authentication of its own — it trusts the POST body completely. The function URL is derived from the Supabase project ref, which ships inside every APK. (SEC-001)

Behind those sit two structural absences that are less dramatic but harder to retrofit. There is no geospatial model: distance_km is a number an admin types in, there are no delivery zones, no serviceability radius, and nothing stops an order being placed 400 km from the kitchen. And there is no observability — no crash reporting, no product analytics, no APM, in any of the four clients. On launch day you would not know anything had broken except by being told.

Finally, the accessibility position is close to zero. Across 325 Dart files there are four semantic labels, all in the customer app; the vendor and rider apps contain none at all. The design system's own muted text colour measures 3.9:1 against white, below the 4.5:1 WCAG AA floor, and it is used for every caption in the product.

Launch readiness verdict

Not production ready

Not because the product is weak — it is unusually strong for its stage — but because four of the thirteen blockers permit uncapped, unrecoverable financial loss from the first paying customer, and a fifth hands an unauthenticated stranger your entire push channel. None of these degrade gracefully at low volume: one exploited vendor coupon, or one COD-heavy day, is enough. Estimated distance to a defensible public launch: 7–10 engineering weeks, of which roughly six are Phase 1.

PAY-001 Payment is a mock, and the server accepts any string as proof of it Customer App · Backend · Checkout → UPI sheet Blocker

Current behaviour

Selecting UPI at checkout opens MockPaymentGateway, a locally drawn bottom sheet with a "Pay" button and a "Simulate a failed payment" link. On success it returns pay_mock_<random hex>. That string is passed to place_order as p_payment_id. The server's entire verification is:

if p_payment_method = 'upi'
   and (p_payment_id is null or length(trim(p_payment_id)) = 0) then
     raise exception 'We couldn''t confirm your payment.';
-- supabase/migrations/0064_a_kitchen_runs_its_own_offer.sql:184

Problem

Any client that can reach place_order — including curl with the anon key extracted from the APK plus a signed-in session — can post p_payment_method: "upi", p_payment_id: "x" and receive a fully valid, paid-status order. The kitchen cooks it, a rider delivers it, the vendor is settled for it and the rider is paid for it. Total loss per order equals food cost plus rider pay plus the vendor's settled net.

Root cause

The gateway seam was designed correctly — PaymentGateway is an interface and the mock lives in the presentation layer precisely so it can be deleted — but the server-side half was never built. Razorpay integration was deferred behind KYC approval, and the placeholder validation ("non-empty string") was never marked as a hard gate.

Recommended solution

  1. Add a payments table: order_ref (your idempotency key), gateway_order_id, gateway_payment_id, signature, amount_paise, status ∈ (created, authorized, captured, failed, refunded), raw_webhook jsonb. RLS on, no policies, all grants revoked.
  2. New RPC create_payment_intent(cart): prices the cart with the same code path place_order uses (extract the pricing block into price_cart(p_restaurant_id, p_items, p_coupon_code) so the quote and the charge can never disagree), calls Razorpay Orders API from an Edge Function with the key in Supabase secrets, and returns {gateway_order_id, amount}.
  3. Client opens the real Razorpay SDK with that gateway_order_id. The razorpay_flutter dependency is already declared in apps/customer/pubspec.yaml.
  4. Verify server-side: an Edge Function receiving Razorpay's webhook recomputes HMAC-SHA256(order_id + "|" + payment_id, key_secret) and compares in constant time. Only that function may set status='captured'.
  5. Change place_order to take a p_payment_ref that must resolve to a captured payment row of exactly the computed total, unconsumed. Make the consumption a select … for update so the same payment cannot back two orders.
  6. Add the reconciliation job: any captured payment with no order after 15 minutes is auto-refunded and alerted on.

Industry reference

Swiggy and Zomato both create the gateway order server-side and treat the client's success callback as a hint only — the order is confirmed by the webhook, which is why both apps show "Confirming payment…" for a beat after the UPI app returns. Never trust the client's word that it paid.

BIZ-001 Settlement pays vendors on pre-discount subtotal — a vendor can fund its own discount from your bank account Backend · Database · run_settlement_batch Blocker

Current behaviour

sum(o.subtotal)::integer as gross_sales
…
v_commission := round(b.gross_sales * b.bps / 10000.0)::integer;
net_payable = gross_sales - commission
-- supabase/migrations/0017_settlements.sql:208, 215

orders.discount exists, is populated by place_order, and is never referenced by the settlement rollup. Migration 0064 then gave vendors the ability to create their own coupons scoped to their own restaurant.

Problem

A vendor creates FREEFOOD, 100% off, no minimum, on their own menu. A customer orders ₹1,000 of food and pays ₹90 (delivery fee + tax). At the weekly rollup that order contributes gross_sales = 1000, commission = 200, net_payable = 800. The platform wires the vendor ₹800 against ₹90 collected. There is no cap, no promotional budget, no approval step, and coupons have no usage limit (BIZ-003), so this is repeatable without bound. It is also indistinguishable from legitimate promotional activity in the admin console, which has no coupon-cost report.

Root cause

Migration 0017 defined gross_sales as "the food value the restaurant sold" at a time when every coupon was platform-issued and platform-funded — under which assumption ignoring the discount is correct. Migration 0064 changed who may issue a coupon and did not revisit who funds one. The two migrations are individually right and jointly wrong.

Recommended solution

  1. Add coupons.funded_by ∈ (platform, restaurant), NOT NULL. Backfill every existing row to platform. The vendor-facing RPC may only ever write restaurant.
  2. Freeze the funder onto the order at purchase time — orders.discount_funded_by — the same way the discount amount is already frozen. A coupon's funding model must not be re-readable later.
  3. Rewrite the rollup: gross_sales = sum(subtotal), vendor_funded_discount = sum(discount) filter (where discount_funded_by='restaurant'), commission = round((gross_sales − vendor_funded_discount) × bps / 10000), net_payable = gross_sales − vendor_funded_discount − commission. Add both new figures as columns so the statement explains itself.
  4. Update the settlement_net_is_consistent check constraint to match, so a wrong rollup cannot be written.
  5. Independently, cap vendor coupons: max discount percent, a mandatory valid_until, and a monthly budget ceiling enforced in the RPC.

Resolution — migration 0074

Items 1–4 are done and applied. coupons.funded_by is NOT NULL with no default — a writer that does not say who pays does not get a row — and the two writers were updated to say it: admin_save_coupon always platform, vendor_save_offer always restaurant. Neither can rewrite the funder of a live campaign; funded_by is deliberately absent from both on conflict do update lists. orders.discount_funded_by is frozen at purchase by place_order and never re-read from the coupon, with a constraint asserting a discount has a funder and an order without one does not.

Verified against the finding's own scenario: three delivered orders of ₹1,000 food, one of them 100% off on the restaurant's own coupon. The old rollup pays ₹2,400 against ₹2,830 collected in fees and tax. The new one pays ₹1,600 — gross 3,000, own offers 1,000, commission 400 on the 2,000 that remains. The vendor's own earnings screen, which carried the identical bug and would otherwise have shown one net figure all week and paid a different one on Monday, returns the same five numbers.

The finding's last sentence — that this is "indistinguishable from legitimate promotional activity in the admin console" — is addressed too: admin_list_settlements returns vendor_funded_discount and the settlements table has an Own offers column. The vendor is told before the fact rather than by a smaller transfer: the offer editor now states, above the save button, that they fund the discount and that commission is charged on what is left after it.

Item 5 (caps, budget ceiling, mandatory valid_until) is BIZ-003 and is not in this migration. This one makes every discount attributable; that one makes it bounded. They are not the same change and the second is worthless without the first.

Industry reference

Zomato's partner dashboard splits every offer into "funded by you" and "funded by Zomato" and shows the restaurant its own promotional spend as a line item on the weekly payout statement. Swiggy requires restaurant-funded offers to be accepted contractually before they can be created. Neither platform lets a merchant discount at the platform's expense.

BIZ-002 Cash on delivery has no reconciliation — the platform pays out twice and collects nothing Backend · Rider App · Payouts Blocker

Current behaviour

payment_method accepts 'cod' and 'upi' (0003_orders_and_coupons.sql:68). A COD order flows through the identical lifecycle. confirm_delivered takes the delivery OTP and marks the order delivered. A search of all 70 migrations and all 325 Dart files finds no occurrence of cash collected, cash in hand, cash deposit, or COD reconciliation — the only hit for "cash" in the rider app is an SVG icon enum (RiderSvgType.cashCollect) that draws a banknote and is not wired to any ledger.

Problem

On a ₹500 COD order the customer hands ₹500 in notes to the rider. Then: run_rider_payout_batch pays the rider rider_pay for the delivery, and run_settlement_batch pays the vendor subtotal − commission. Both come from platform funds. The ₹500 remains in the rider's pocket with no system record that it was ever collected. The platform's loss on every COD order is the full amount collected. In Indian food delivery COD is typically 25–40% of order volume at launch.

Root cause

COD was modelled as a property of an order rather than as an obligation on a rider. The delivery lifecycle (migration 0049) is otherwise rigorous, but it closes at "the food changed hands" and has no concept of "the money changed hands in the other direction".

Recommended solution

  1. Ledger first. rider_cash_ledger(id, partner_email, order_id, kind ∈ (collected, deposited, adjustment), amount, created_at, deposit_ref). A rider's cash in hand is sum(collected) − sum(deposited) ± adjustments — never a stored balance that can drift.
  2. Write on delivery. Extend confirm_delivered: when orders.payment_method = 'cod', insert a collected row for orders.total in the same transaction. Delivery and collection become one atomic fact.
  3. Show it. Rider app: a persistent "Cash in hand ₹X" chip on the Earnings tab, and a hard block on accepting new COD jobs above a configurable ceiling (₹3,000–₹5,000 is the industry norm).
  4. Settle it. Net cash in hand off the weekly payout: payout = earnings − cash_outstanding, floored at zero, with the remainder carried. Admin console gets a Cash Reconciliation page listing every rider's outstanding balance and a "record deposit" action writing the deposited row with a UTR.
  5. Guard it. Deactivating a rider with non-zero cash in hand must be refused, the same way going offline mid-job already is.

Industry reference

Zomato and Swiggy both surface a live "Cash in hand" figure in the partner app, block further COD assignment past a threshold, and net the balance against the weekly payout. Rapido does the same for cash rides. This is table stakes, not an optimisation.

SEC-001 The push notification Edge Function authenticates nothing — anyone can notify any user Backend · supabase/functions/send-notification Blocker

Current behaviour

Deno.serve(async (req) => {
  let payload: WebhookPayload;
  try { payload = await req.json(); }
  catch { return new Response("Bad request", { status: 400 }); }
  const n = payload.record;
  // no header check, no shared secret, no JWT — the body is trusted
-- supabase/functions/send-notification/index.ts:145

The function is deployed --no-verify-jwt (documented in ZOMATO_PARITY.md §B0) so that the database webhook can reach it, and it adds no authentication of its own. It reads the recipient straight out of the posted JSON, looks up that recipient's device tokens using the service role key, and sends whatever title and body the caller supplied.

Problem

Supabase function URLs are https://<project-ref>.supabase.co/functions/v1/send-notification, and the project ref is a compile-time default in apps/customer/lib/app/env.dart — recoverable from any APK in under a minute. An attacker can then:

  • Push arbitrary notifications to every restaurant tablet — restaurant ids are public (r1, r3, …) and trivially enumerable from the catalog.
  • Push to any rider whose email they can guess or harvest.
  • Send "Your order is at the door — share code 4471 with your rider" style phishing, defeating the delivery-OTP protection the team built in migration 0049.
  • Exhaust the FCM quota and the function's invocation budget as a denial of service on your own push channel.

Root cause

--no-verify-jwt was required because Supabase database webhooks historically did not attach a user JWT. The correct compensating control — a shared secret header — was not added, and the tracker records the other function (send-order-push) as the known deployment hazard while this one was treated as done.

Recommended solution

  1. Generate a high-entropy secret: supabase secrets set NOTIFY_WEBHOOK_SECRET=….
  2. First statement in the handler: if (req.headers.get("x-notify-secret") !== Deno.env.get("NOTIFY_WEBHOOK_SECRET")) return new Response("Forbidden", {status: 403}). Compare with a constant-time helper, not !==, if you want to be thorough.
  3. Add that header to the notifications INSERT webhook config in the Supabase dashboard.
  4. Do not trust the posted record at all. Take only payload.record.id from the body and re-read the row from the database with the service key. The webhook then cannot be used to fabricate a notification even if the secret leaks.
  5. Complete the outstanding supabase functions delete send-order-push — a live, unwired endpoint is the same hazard pointing elsewhere.
  6. Rate-limit the function per recipient (Supabase Edge supports this via a KV counter or a Postgres check) so a leaked secret cannot become a mass-notification event.

Industry reference

Standard practice for any webhook receiver — Stripe, Razorpay, GitHub all sign the payload and require the receiver to verify. Razorpay's own webhook integration, which this project will need for PAY-001, uses exactly this pattern; build both at once.

RID-001 Rider location has no foreground service — live tracking stops the moment the rider opens their maps app Rider App · Location reporter Blocker

Current behaviour

Geolocator.getPositionStream(
  locationSettings: const LocationSettings(
    accuracy: LocationAccuracy.high, distanceFilter: 30))
-- apps/rider/lib/features/jobs/data/location_reporter.dart:62

A plain LocationSettings, not AndroidSettings with a foregroundNotificationConfig. The manifest declares ACCESS_FINE_LOCATION and ACCESS_COARSE_LOCATION only — no FOREGROUND_SERVICE, no FOREGROUND_SERVICE_LOCATION, and (by explicit design decision) no ACCESS_BACKGROUND_LOCATION. Permission is requested as whileInUse.

Problem

Android throttles background location for a whileInUse app to a few updates per hour, and on Android 10+ typically stops them altogether once the app leaves the foreground. The rider app's own navigation feature is a geo: hand-off that launches Google Maps over it. So the product's designed happy path is: rider accepts job → taps Navigate → Zopiq goes to the background → location updates stop → the customer's live map freezes for the entire journey → the dynamic ETA (orders.eta_at, migration 0057) recomputes from a stale position and drifts.

Every downstream feature that consumes rider_locations — the live delivery map, the moving-ETA card, the dispatcher's nearest-rider ranking in 0056_the_job_finds_the_rider.sql — silently degrades. Considerable engineering investment in B3 dispatch is neutralised by this one omission.

Root cause

The manifest comment states the reasoning: background location was avoided to dodge Google Play's background-location review. That instinct is right, but the conclusion is wrong — a foreground service with a visible notification is the sanctioned alternative and does not require ACCESS_BACKGROUND_LOCATION at all.

Recommended solution

  1. Manifest: add <uses-permission android:name="android.permission.FOREGROUND_SERVICE"/> and …FOREGROUND_SERVICE_LOCATION (mandatory from Android 14).
  2. Swap the settings object for AndroidSettings(accuracy: high, distanceFilter: 30, foregroundNotificationConfig: ForegroundNotificationConfig(notificationTitle: "On a delivery", notificationText: "Sharing your location with the customer", enableWakeLock: true)). geolocator already supports this; no new dependency.
  3. Start the service on claimed and stop it on delivered or cancelled — the existing setCarrying gate is already the right hook.
  4. Add an OEM battery-optimisation prompt on first job (Xiaomi, Oppo, Vivo and Samsung all kill unwhitelisted services aggressively, and those are the majority of the Indian rider handset fleet).
  5. Store a location trail, not just the latest fix — see DAT-004.
  6. Write the Play Console data-safety declaration for foreground location; it is a disclosure, not a review gate.

Resolution — app change, no migration

Items 1 to 4 are done. The manifest now declares FOREGROUND_SERVICE, FOREGROUND_SERVICE_LOCATION and WAKE_LOCK; ACCESS_BACKGROUND_LOCATION is still deliberately absent, which is the whole point of the finding's root-cause paragraph. The stream in location_reporter.dart now takes AndroidSettings with a ForegroundNotificationConfig — "On a delivery / Sharing your location with the customer", setOngoing so it cannot be swiped away while it is running, and enableWakeLock so the fixes arrive as they happen rather than in a burst when the phone next wakes. Item 3 needed nothing: setCarrying was already the gate, and cancelling the stream is what tears the service and the notification down.

Current behaviour

Of 140 distinct security definer functions, 94 carry an explicit revoke … from public. 51 do not. Postgres grants EXECUTE to PUBLIC by default on function creation, and Supabase's anon role is a member of PUBLIC — so those 51 are callable by anyone holding the anon key, which ships in every APK.   1. Write one migration that revokes all on function … from public, anon, authenticated for every function in public, then re-grants execute to exactly the role each one needs. Generate it from pg_proc, do not hand-list.

The good news about the bottlenecks

Every constraint listed above is a known, local problem with a standard remedy — an index, a bound, a partition, a queue. None of them require unpicking a bad abstraction, because there isn't one. Putting business rules in Postgres is what makes the 10k → 100k work tractable: the rules do not have to be re-derived in three clients when the storage underneath them changes.
