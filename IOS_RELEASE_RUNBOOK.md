**Written 2026-08-17, on Windows, by a session that cannot compile any of this.**
Hand this file to the Claude session running on the Mac. It is the current
queue; `IOS_HANDOVER.md` is the archaeology — what was built, why, and what was

the ones here.

## 0. Who does what

The Mac has the compiler, the Xcode GUI, the signing identity and the phone.
Claude has the codebase and can read, edit and reason about every file. The
division that works:

- **Claude should**: run builds, read errors, fix Swift and Dart, edit plists and
  xcconfigs, write the App Store metadata, and say precisely what it changed.
- **The human must**: click through Xcode's GUI (targets, capabilities, signing),
  answer interactive prompts (`supabase login`), upload to App Store Connect,
  and make the judgement calls in §5 that involve Apple's reviewers.

**The highest-value thing Claude can do is run a build and report the exact
error**, rather than reasoning ahead of the compiler. Nothing in this repo's iOS
layer was compiled until recently, so real error messages are worth more than
any amount of prediction.

## 2. Rules that will bite you

These are not style preferences. Each one has already cost this project time.

1. **The version freeze is absolute and binds in both directions.** Do not run
   `flutter pub upgrade`. Do not bump a plugin to resolve a CocoaPods conflict.
   Do not *downgrade* Flutter to match a version written in some older document.
   If CocoaPods demands a version change, **stop and report what it wanted** —
   that is a decision for the project owner, not a build fix.
2. **`plutil -extract KEY json FILE` rewrites the file in place.** It looks
   read-only and is not. It has already silently replaced all three `Info.plist`
   files in one session; only the fact they were committed saved them. Always
   pass `-o -` to print instead. The failure surfaces as a `flutter` tool crash
   deep in `PlistParser` that names neither `plutil` nor your plist.
3. **Do not run `dart format`.** The installed formatter rewrites unrelated code
   and produces a diff nobody asked for. Hand-format to match the file.
4. **The Flutter test suites are a real merge gate** — but they are **already red
   on main** as of 2026-08-15 (roughly 116 of 133 in customer at a clean HEAD).
   ⚠️ **Baseline the suite at a stashed HEAD before blaming your own change.**
   An earlier handover recorded 133/35/62 all passing on 2026-08-02; that is no
   longer true and the regression is not yours. Do not "fix" tests by deleting
   them, and do not write new ones — this project hands over manual steps
   instead.
5. **Prefer fixing the iOS side over changing shared Dart.** Shared Dart is
   proven on Android in production; iOS scaffolding is not proven anywhere.
   When something breaks, the odds favour the new code.

## 3. Phase A — get all three running on a device

### A1. Pull and resolve

```bash
cd /path/to/zopiqnow
git pull
flutter --version          # expect 3.44.8; do NOT change it
flutter pub get            # NOT upgrade
```

### A2. Signing

In Xcode, for each of `apps/customer/ios/Runner.xcworkspace`,
`apps/rider/…`, `apps/vendor/…`:

- **Signing & Capabilities** → tick *Automatically manage signing* → select the
  team. This sets `DEVELOPMENT_TEAM`, which is currently unset in all three
  projects.
- Confirm the bundle ids, which are deliberate and must not be "tidied":
  - customer `com.siteonlab.zopiqnow`
  - rider `com.siteonlab.zopiqRider`
  - vendor `com.siteonlab.zopiqVendor`

  The camelCase exists because Apple forbids the underscores the Android
  application ids carry.

- Add **Push Notifications** capability, and **Background Modes** → *Remote
  notifications* (plus *Location updates* on the rider). The plists already
  declare the background modes; the entitlement is a separate thing Xcode owns.

**Verify:** signing is what finally proves `Runner.entitlements`. After the first
signed build, confirm `aps-environment` is actually present:

```bash
codesign -d --entitlements - build/ios/iphoneos/Runner.app
```

If `aps-environment` is missing, push will fail later in a way that looks like a
server problem. Catch it here.

> This command used to pipe through `plutil -p -o - -- -`, which prints an empty
> result whether the entitlements are absent *or* perfectly correct. Confirmed
> 2026-08-20 on a binary that does carry `aps-environment: production`. Read
> `codesign`'s own output instead — it is already legible.
>
> **Done for customer on 2026-08-20**: `aps-environment` is `production`. Rider
> and vendor are still unchecked, because neither has been signed yet.

### A3. Run

```bash
cd apps/customer && flutter run -d <device>
cd apps/rider    && flutter run -d <device>
cd apps/vendor   && flutter run -d <device>
```

**Expect Swift compile errors.** The last person to point a compiler at this code
found a real bug within minutes — `ZopiqLiveCardPlugin.swift` called
`registrar.addMethodCallDelegate(instance, on: channel)` when the label is
`channel:`. It had never compiled because nothing had ever compiled it. Budget
for a few more of that class. They are cheap once the compiler is looking.

**Smoke-test by hand** (this project does not keep Flutter tests for these):

- Customer: sign in with email OTP; set a location; open a restaurant; add to
  cart; reach the payment screen. Confirm the launch screen is **brand orange,
  not white** — that was fixed on 2026-08-17 in `a1fb228` and has never been seen
  on a device.
- Rider: sign in; confirm the map draws; confirm *Navigate* opens Apple Maps.
  ⚠️ A `geo:` URI that no iPhone handles was one of the five Android-only bugs
  found during the port — the iOS path exists now, but nobody has watched it.
- Vendor: sign in; confirm the orders board loads and a new order **rings**.

### A4. Checking a feed on the simulator, without a device or an OTP

Not everything needs the phone. Anything that is Dart plus a network call — the
town lock is the worked example — can be watched on the simulator, and two facts
make it cheap:

**Home is not behind sign-in.** `_protectedPrefixes` in `router.dart` covers
checkout, orders, addresses and favourites; browsing the catalogue is open. So
no email OTP is needed to look at a feed.

**The selected address is plain `SharedPreferences`**, under the key
`flutter.zopiq.location.selected_address` — note the `flutter.` prefix the plugin
adds. Seed it and the app opens on whatever town you like:

```bash
SIM=<device-udid>
xcrun simctl terminate  $SIM com.siteonlab.zopiqnow
xcrun simctl uninstall  $SIM com.siteonlab.zopiqnow   # ← see the trap below
xcrun simctl install    $SIM apps/customer/build/ios/iphonesimulator/Runner.app
xcrun simctl privacy    $SIM grant location-always com.siteonlab.zopiqnow
# write {"id","line1","city","latitude","longitude","label","delivery_notes",
#        "service_area_id"} as a JSON *string* into
#   <data-container>/Library/Preferences/com.siteonlab.zopiqnow.plist
xcrun simctl launch     $SIM com.siteonlab.zopiqnow
xcrun simctl io         $SIM screenshot out.png
```

Leave `service_area_id` **null**. The app then resolves the town itself through
`delivery_area_check` and writes the answer back — which is the thing worth
watching, and it is real evidence rather than a value you fed it.

⚠️ **The trap: a running app clobbers the file.** Flutter's `SharedPreferences`
holds the whole map in memory and flushes it on exit, so seeding a new address
while the app is alive — or seeding it and launching before the old process has
fully gone — silently restores the previous town. It costs a full cycle each
time, and the screenshot looks plausible. Uninstall first (that wipes the
container), then seed, then launch. Verify the file *before* launching, and read
the header on the screenshot to confirm which town actually loaded.

Grant `location-always` too, or a fresh install raises the permission alert over
the feed — and per `IOS_HANDOVER.md` §0, an unanswered alert blocks the whole
simulator.

**What a simulator cannot show you:** APNs, Live Activities, real GPS drift, and
anything about signing. Those still need the phone.

## 4. Phase B — make push actually arrive

This is the phase most likely to be declared "done" while silently broken. Work
it as a chain and verify each link before moving on.

### B1. APNs key

Apple Developer portal → Keys → **create an APNs Auth Key (`.p8`)**. You need the
key file, the **Key ID**, and your **Team ID**.

Firebase console → Project Settings → Cloud Messaging → iOS app configuration →
upload it. ⚠️ **One upload.** All three apps live in `zopiq-de276`.

The `.p8` downloads exactly once. Store it somewhere durable and **not in this
repo — the repository is public.**

### B2. Redeploy the edge function

⚠️ **The step most easily forgotten, and it invalidates everything downstream.**
Until it runs, the `apns` block in the function has no effect and iOS push
cannot arrive no matter how perfect the signing is.

```bash
supabase login                                   # interactive — needs the human
supabase link --project-ref ofjjuzrxnksbyglzwaah
supabase functions deploy send-notification
```

### B3. Walk the chain

Do not guess. Verify in this order, stopping at the first link that fails:

1. **APNs token** — device registers with Apple.
2. **FCM token** — Firebase exchanges it.
3. **`device_tokens` row with `platform='ios'`** — check in Supabase. A token
   hardcoded as `'android'` was one of the five bugs found during the port; the
   fix is in, but confirm the row says `ios`.
4. **Webhook fired** — the DB trigger ran.
5. **Function logs** — `send-notification` was invoked and what it returned.

Then test with the app (a) foregrounded, (b) backgrounded, and (c) **killed**.
The killed case is the one that finds real bugs: native code in `android/app` was
unreachable from a killed app on Android, which is why the live card became a
plugin package. Confirm the iOS equivalent survives.

## 5. Phase C — the Live Activity (customer only)

**Do this only after Phase A passes on a device.** An extension added earlier
turns any single failure into two candidates.

This is the one part that cannot be done by dropping files in, because an app
extension is an Xcode target and `project.pbxproj` was deliberately never
hand-edited — hand-writing target UUIDs reliably corrupts a project.

With `apps/customer/ios/Runner.xcworkspace` open:

1. **File → New → Target → Widget Extension**, named exactly
   **`ZopiqLiveActivity`**. Tick *Include Live Activity*. Untick *Include
   Configuration Intent*. Embed in `Runner`.
2. Delete Xcode's template files. Add the ones already written at
   `apps/customer/ios/ZopiqLiveActivity/` — `ZopiqLiveActivity.swift`,
   `ZopiqLiveActivityBundle.swift`, `Info.plist` — and point the target's
   `INFOPLIST_FILE` at that plist.
3. ⚠️ **The critical checkbox.** Add
   `packages/zopiq_live_card/ios/Classes/ZopiqLiveCardAttributes.swift` to the
   `ZopiqLiveActivity` target **as a reference, not a copy**. The app and the
   extension must compile the *same* file. Two copies compile cleanly and then
   fail to match at runtime: the activity starts and renders nothing, which is a
   far worse afternoon than a compile error.
4. Deployment target **14.0**, matching the app. Bundle id
   `com.siteonlab.zopiqnow.ZopiqLiveActivity`.
5. The extension's `CFBundleShortVersionString` / `CFBundleVersion` are wired to
   `$(FLUTTER_BUILD_NAME)` / `$(FLUTTER_BUILD_NUMBER)`. **iOS refuses to install
   an extension whose version does not match its container app, and the error
   names neither.** If install fails mysteriously, check this first.

Live Activities do not work usefully in the simulator. Test on a real device.

## 6. Phase D — publish

New ground: `IOS_HANDOVER.md` stops before this. Two traps here will cost days if
they are met at submission time rather than now.

> **Both traps were decided on 2026-08-20, and the metadata is written.**
> Scope is the **customer app only** (Trap 2), and the reviewer signs in with a
> **fixed-OTP demo account** (Trap 1). Every field App Store Connect asks for —
> name, subtitle, keywords, description, review notes, the App Privacy answers,
> the screenshot list — is written out ready to paste in
> **`IOS_APP_STORE_LISTING.md`**. Work from that file for D1–D3; the sections
> below stay as the reasoning behind it.

### ⚠️ D0. Read these two before writing any metadata

**Trap 1 — App Review cannot log in.** The customer app signs in with an **email
OTP**; the reviewer will enter an address, wait for a code, and be stuck. An app
that a reviewer cannot get past the login screen of is rejected, quickly and
repeatedly, under Guideline 2.1.

You must give them a working way in. Pick one, before submitting:

- A **demo account whose OTP is fixed**, plus the address and code in App Store
  Connect's *App Review Information → Sign-in required* fields. Supabase's GoTrue
  supports pre-set OTPs for specific test addresses — this is the cleanest
  option and it does not weaken real accounts.
- Or a reviewer-only account with a **password** path.

Do **not** tell the reviewer to email you for a code. That is a rejection.

**Trap 2 — the staff apps may not belong on the public App Store at all.**
Rider and vendor are internal tools for Zopiq's own riders and restaurants. Apple
rejects apps with no use for the general public under Guideline 4.2, and
"business app, sign-in required, no public value" is a well-worn rejection.

Three routes, and the choice is the project owner's:

| Route | Fits |
|---|---|
| **Apple Business Manager / Custom Apps** | Cleanest for genuinely internal tools; distributed privately, no public review of usefulness |
| **Public App Store with a demo account** | Works if you can argue the app serves a real external audience (independent riders, partner restaurants) |
| **TestFlight only** | Fine short-term for the 14-day-tester-style rollout; not a permanent answer |

Given Zopiq's riders and restaurants are independent businesses rather than
employees, the public route is arguable — but **decide deliberately and put the
argument in the review notes**, rather than submitting three apps and finding out.

### D1. App Store Connect records

Create three apps, each with its bundle id from §A2. Fill in:

- **Name, subtitle, category** — Food & Drink for customer; Business for rider
  and vendor.
- **Privacy Policy URL**: `https://nayansuthar-1.github.io/zopiqnow/privacy.html`
- **Support URL** and **Terms**:
  `https://nayansuthar-1.github.io/zopiqnow/terms.html`
- **Account deletion**: `https://nayansuthar-1.github.io/zopiqnow/delete-account.html`
  — Apple requires an in-app deletion route *and* accepts this page as the
  documented path. All three URLs are live and already serve both stores.

### D2. App Privacy questionnaire

Answer it from what the apps actually declare, not from memory. The customer app
collects **precise location**, **contact info** (email, phone) and **purchase
history**; the rider app collects **precise location in the background**. Getting
this wrong is a post-release enforcement problem, not a review one — which makes
it easier to get wrong and worse to discover.

Background location on the rider app draws extra scrutiny. Be ready to explain,
in one sentence, that it exists to show customers where their order is.

### D3. Screenshots

Required at 6.7" and, depending on Apple's current rules, 5.5". Capture on a real
device from the running app — these can be produced during Phase A rather than
as a separate exercise.

### D4. Archive and upload

```bash
cd apps/customer
flutter build ipa --release
```

Then **Xcode → Organizer → Distribute App**, or `xcrun altool` / Transporter.
Repeat for rider and vendor.

- **Export compliance**: the apps use HTTPS only and qualify for the standard
  exemption, but the question must still be answered on every build. Setting
  `ITSAppUsesNonExemptEncryption` to `false` in each `Info.plist` stops it being
  asked every single upload — worth doing once.
- **Build numbers** come from `$(FLUTTER_BUILD_NUMBER)`. App Store Connect
  rejects a reused build number with a message that arrives by email several
  minutes after the upload appears to have succeeded.

### D5. TestFlight first

Push all three to TestFlight internal testing and put them on real phones before
submitting for review. The Android side is already in closed testing; matching
that shape on iOS is the low-risk path.
